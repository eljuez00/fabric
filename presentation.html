Level 2

Author — writes the tool. You're still the runtime.

Same chat window, same model as Level 1 — the only thing that changed is what was asked for. This is prepared work, not a live run: the spec below is what produced merge.py, shown in full underneath it.

The spec

Take these two CSVs and this SQLite table and: - load jobs.csv and candidates.csv with pandas - query enrichment.db with a SQL SELECT against the profiles table - join jobs -> candidates -> profiles into one row per candidate - don't silently drop mismatches: compute and print how many candidates matched a profile, how many didn't, and how many profiles went unused - write the merged view out as BOTH an HTML file and an Excel file

The result — merge.py

"""
merge.py
--------
Level 2 - Author. Reads three shared sources - two flat
files and a SQLite database - and produces one merged
view, written out as both HTML and Excel.

    ../jobs.csv       -> pandas  (exported report)
    ../candidates.csv -> pandas  (exported report)
    ../enrichment.db   -> SQL     (a live system)
"""

import sqlite3
from pathlib import Path
import pandas as pd

HERE = Path(__file__).parent
ROOT = HERE.parent

# 1. Load the two exported reports with pandas.
jobs = pd.read_csv(ROOT / "jobs.csv")
candidates = pd.read_csv(ROOT / "candidates.csv")

# 2. Query the live system with a real SQL SELECT.
SELECT_PROFILES_SQL = """
    SELECT profile_id, name, current_title,
           current_company, years_experience
    FROM profiles
"""
conn = sqlite3.connect(ROOT / "enrichment.db")
profiles = pd.read_sql_query(SELECT_PROFILES_SQL, conn)
conn.close()

# 3. jobs -> candidates: a clean merge on job_id.
candidates_with_jobs = candidates.merge(
    jobs, on="job_id", how="left", suffixes=("", "_job")
)

# 4. candidates -> profiles on full name - the messy
#    half. A naive exact-name join surfaces every
#    mismatch instead of hiding it.
merged = candidates_with_jobs.merge(
    profiles, left_on="full_name", right_on="name",
    how="left", suffixes=("", "_profile")
)

# 5. Reconciliation summary - compute it, don't
#    assume it.
matched = merged[merged["name"].notna()]
unmatched = merged[merged["name"].isna()]
matched_ids = set(matched["profile_id"])
unused = profiles[~profiles["profile_id"].isin(matched_ids)]

print(f"Matched: {len(matched)}  "
      f"Unmatched: {len(unmatched)}  "
      f"Unused profiles: {len(unused)}")

# 6. Write the merged view out as HTML and Excel.
talent_view = merged[[
    "candidate_id", "full_name", "email", "job_id",
    "title", "department", "location", "stage",
    "current_title", "current_company",
    "years_experience",
]].rename(columns={"title": "job_title"})

talent_view.to_html(HERE / "merged.html", index=False)
talent_view.to_excel(HERE / "merged.xlsx", index=False)
The hinge

Levels 1 and 2 are a request. Level 3 is access.

Levels 1 & 2

Same chat. Same model.

You ask for an answer, or you ask for a tool. Either way, the model lives in a chat window. It reasons or it writes — but you execute, you move files, you press run.

→
Level 3

The model gets access.

Not a smarter model — a model that now lives in your environment, via a CLI or its parent app. It reaches into the filesystem, runs what it writes, iterates on its own errors, calls out to services.

That's the chapter break of this talk: not a capability jump, an access jump.

Level 3

Agent — writes and runs, iterates, calls out

local access

A Level 3 agent reaches the exact same merged outcome as level2-author/merge.py — but nobody exports a file or runs a script by hand. It goes one step further, too: instead of waiting on jobs.csv/candidates.csv to be exported at all, it reads the source system's WSDL and calls the SOAP endpoint directly, then runs the whole pipeline itself. See level3-agent/bonus-direct-wsdl.md.

  • Same destination as Level 2 — the merged talent view — reached with the human removed from the loop.
  • Writing real integration code (auth, pagination, request envelopes) most humans wouldn't hand-write.
  • The human's job collapses to two things: describe intent, verify output.

Takeaway

What moved, level by level — and where to watch it

  • Level 1: the model reasons. Level 2: the model writes the tool. Level 3: the model writes and runs it.
  • The chapter break wasn't a smarter model — it was access. That's why Level 3 needs governance and Levels 1–2 don't.
  • At Level 1 you judge the analysis. At Level 2 you read the code before running it. At Level 3, the agent has already acted before you get to check.
Governance — Level 3 only

Auto-moving data between systems is exactly the kind of data-movement pattern an admin must control: scoped access, an audit trail, a human sign-off on what's allowed to move where. This is the cost of the autonomy Level 3 buys you.

The deeper win

The real agentic-development payoff goes one step further than anything shown so far: an agent that reads a source system's WSDL and calls its SOAP endpoint directly — skipping the export step entirely, building real integration code a human wouldn't hand-write. See level3-agent/bonus-direct-wsdl.md.
