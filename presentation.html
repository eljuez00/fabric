A talk about agentic development

fabric

Recruiting data as the vehicle. Three levels of what a Large Language Model (LLM) can be asked to do as the subject. Same dataset, three artifacts, one through-line: at each level, you hand over one more thing.

Synthetic data only — built to illustrate a concept for a talk.
The spine of this talk

Three levels. One more thing handed over at each.

LevelRoleModel now ownsYou still own
1 — Analyst reasons over your data the thinking get the data in, act on the answer
2 — Author writes the code too thinking + code run it: feed files, execute, debug
3 — Agent runs it too, local access thinking + code + execution —

At every level you do the same two things: say what you want, and check what comes back. Everything between those migrates across the line.

Level 1

Analyst — reasons over data you bring it

nothing executes

The whole level is one line: input → prompt → output. The model reads a table and reasons back — it never touches a filesystem, never runs a query. The human did all the surrounding work: pulled the data, opened the model, and will still have to decide what to do with the answer.

Also Level 1 — and not recommended

Sometimes "the table" is more than one file: paste the candidate export and a profile export into the same chat and ask the model to reconcile them itself, in its head. Still Level 1 — nothing executes, it's reasoning over pasted text, not running a query — but it won't resolve the same edge cases the same way twice, there's no file left behind to check, and it quietly breaks past a page or two of data. Worth doing anyway: a second pair of eyes, or a deeper pass than you want to do by hand. That fragility, not the single-table case above, is the real argument for Level 2.

Level 2

Author — writes the tool. You're still the runtime.

Same chat window, same model as Level 1 — the only thing that changed is what was asked for. This is prepared work, not a live run: the spec below is what produced merge.py, shown in full underneath it — it queries the database with a SQL (Structured Query Language) SELECT and writes an HTML (HyperText Markup Language) file plus an Excel file.

The spec

Take these two CSVs and this SQLite table and: - load jobs.csv and candidates.csv with pandas - query enrichment.db with a SQL SELECT against the profiles table - join jobs -> candidates -> profiles into one row per candidate - don't silently drop mismatches: compute and print how many candidates matched a profile, how many didn't, and how many profiles went unused - also compute the same stage-count / bottleneck check Level 1 did by hand - automatically - write the merged view out as BOTH an HTML file and an Excel file

The result — merge.py

"""
merge.py
--------
Level 2 - Author. Reads three shared sources - two flat
files and a SQLite database - and produces one merged
view, written out as both HTML and Excel. Whether it's
one source or five doesn't change the shape of the work:
load, join, reconcile, write.

    ../jobs.csv       -> pandas  (exported report)
    ../candidates.csv -> pandas  (exported report)
    ../enrichment.db   -> SQL     (a live system)
"""

import sqlite3
from pathlib import Path
import pandas as pd

HERE = Path(__file__).parent
ROOT = HERE.parent

# 1. Load the two exported reports with pandas.
jobs = pd.read_csv(ROOT / "jobs.csv")
candidates = pd.read_csv(ROOT / "candidates.csv")

# 2. Query the live system with a real SQL SELECT.
SELECT_PROFILES_SQL = """
    SELECT profile_id, name, current_title,
           current_company, years_experience
    FROM profiles
"""
conn = sqlite3.connect(ROOT / "enrichment.db")
profiles = pd.read_sql_query(SELECT_PROFILES_SQL, conn)
conn.close()

# 3. jobs -> candidates: a clean merge on job_id.
candidates_with_jobs = candidates.merge(
    jobs, on="job_id", how="left", suffixes=("", "_job")
)

# 4. candidates -> profiles on full name - the messy
#    half. A naive exact-name join surfaces every
#    mismatch instead of hiding it.
merged = candidates_with_jobs.merge(
    profiles, left_on="full_name", right_on="name",
    how="left", suffixes=("", "_profile")
)

# 5. Reconciliation summary - compute it, don't
#    assume it.
matched = merged[merged["name"].notna()]
unmatched = merged[merged["name"].isna()]
matched_ids = set(matched["profile_id"])
unused = profiles[~profiles["profile_id"].isin(matched_ids)]

print(f"Matched: {len(matched)}  "
      f"Unmatched: {len(unmatched)}  "
      f"Unused profiles: {len(unused)}")

# 6. Level 1's reasoning, folded in and automated:
#    a .groupby() for stage counts, a boolean mask
#    for the on-hold-but-still-active bottleneck.
stage_counts = candidates["stage"].value_counts()
stalled = candidates_with_jobs[
    (candidates_with_jobs["status"] == "On Hold")
    & (candidates_with_jobs["stage"] != "Applied")
]
print(stage_counts.to_string())
print(f"Stalled-but-active reqs: {stalled['job_id'].nunique()}")

# 7. Write the merged view + analysis as HTML and Excel.
talent_view = merged[[
    "candidate_id", "full_name", "email", "job_id",
    "title", "department", "location", "stage",
    "current_title", "current_company",
    "years_experience",
]].rename(columns={"title": "job_title"})

talent_view.to_html(HERE / "merged.html", index=False)
talent_view.to_excel(HERE / "merged.xlsx", index=False)
  • One API, many shapes. read_csv, read_sql_query, read_excel all hand back the same kind of table — a flat file and a live database become interchangeable once loaded.
  • .merge() is a real relational join (inner/left/right/outer) with no hand-written SQL once the data's in memory.
  • Boolean masks filter thousands of rows as fast as one — status == "On Hold" replaces a manual loop entirely.
  • Output format is a parameter, not a rewrite — the same table writes to .to_csv(), .to_html(), .to_excel(), or .to_sql().
Why code, not another chat message

The classic case: "I have to prepare this report every Monday." Pasting three files into a chat and hoping the model resolves the same name mismatches the same way, every week, is Level 1's fragile flavor stretched out over time. A script doesn't improvise — same three inputs, same join, same output, every Monday. That determinism is the whole point of asking for code instead of asking the question again.

The hinge

Levels 1 and 2 are a request. Level 3 is access.

Levels 1 & 2

Same chat. Same model.

You ask for an answer, or you ask for a tool. Either way, the model lives in a chat window. It reasons or it writes — but you execute, you move files, you press run.

→
Level 3

The model gets access.

Not a smarter model — a model that now lives in your environment, via a Command-Line Interface (CLI) or its parent app. It reaches into the filesystem, runs what it writes, iterates on its own errors, calls out to services.

That's the chapter break of this talk: not a capability jump, an access jump.

Level 3

Agent — a workspace, not just a script

full agentic access — workspace, or the machine itself

Level 3 isn't "the agent runs merge.py for you." It's the agent given a small, scoped workspace — a directory it can read from and write to — and left to do all of the development itself: rebuild what Level 1 and Level 2 did as steps in one run, not two hand-offs.

The workspace

workspace/
├── inputs/    read-only copies of the three
│              shared source files
├── scratch/   read-write: scripts the agent
│              writes and re-runs
└── output/    read-write: the merged view it
               produces
  • Reads all three shared sources itself — no human exporting a file.
  • Writes the merge, runs it, reads its own error, fixes it, re-runs — the debugging loop that was the human's job at Level 2.
  • A lot of Level 2's lifting moves here: running the tool, feeding it files, and debugging it are now the agent's job, not the human's.
Agentic safety — local access

Scope the workspace so the agent can only touch this directory, not the rest of the filesystem. Log everything it reads, runs, and writes — at Level 3 it acts before a human gets to check. Treat network access (calling an external service) as a separate, harder-reviewed grant from filesystem access.

Small bonus

Go one step further than Level 2 ever could: skip jobs.csv/candidates.csv as exports entirely. The agent reads the source system's Web Services Description Language (WSDL) file and calls its Simple Object Access Protocol (SOAP) endpoint directly — and does the data wrangling that takes, too: a SOAP response comes back as XML, not a table, so the agent has to parse and reshape it into the same rows merge.py expects before the join logic can even run. Real development end to end, inside its own workspace — including skipping the step of building a custom analytics/reporting extract inside the Applicant Tracking System's (ATS's) own admin console, which is still a human-maintained export either way. See level3-agent/bonus-direct-wsdl.md.

Takeaway

What moved, level by level — and where to watch it

  • Level 1: the model reasons. Level 2: the model writes the tool. Level 3: the model writes and runs it.
  • The chapter break wasn't a smarter model — it was access. That's why Level 3 needs governance and Levels 1–2 don't.
  • At Level 1 you judge the analysis. At Level 2 you read the code before running it. At Level 3, the agent has already acted before you get to check.
Governance — Level 3 only

Auto-moving data between systems is exactly the kind of data-movement pattern an admin must control: scoped access, an audit trail, a human sign-off on what's allowed to move where. This is the cost of the autonomy Level 3 buys you.

The deeper win — recap

The furthest the agent goes: skip the export step entirely, call the source system directly, and wrangle the response itself — Level 3's small bonus — building real integration code a human wouldn't hand-write, in a workspace scoped enough that it's safe to hand over.
